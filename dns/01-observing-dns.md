# Stage 1: Observing DNS on the wire

**Lab:** Kali Linux VM (VirtualBox, NAT networking). The VM's address is `10.0.2.15`; its resolvers are assigned by NetworkManager.
**Date:** 2026-11-04

## Goal

I already understood DNS from the textbook. This stage is about *seeing* a lookup happen on the network, and learning to read `dig` and `tcpdump` output without being overwhelmed by it.

## Tools used

| Tool | What it does | How I used it |
|---|---|---|
| `dig` | Sends a DNS question straight to a resolver and prints the full reply (flags, TTL, timing, which server answered). It does not use a local cache. | `dig google.com` |
| `tcpdump` | Captures packets on an interface. | `sudo tcpdump -i eth0 -n port 53` (`-n` stops it doing its own lookups; `port 53` shows DNS only) |
| `/etc/resolv.conf` | Lists the resolvers the OS asks. Here it is generated by NetworkManager. | `cat /etc/resolv.conf` |

My resolvers, in order: `192.168.1.1` (router, IPv4), then a private IPv6 resolver as the fallback.

## Reading one query and its response

Query (VM to resolver):

```
10.0.2.15.55277 > 192.168.1.1.53: 12816+ A? google.com.
```

Response (resolver to VM):

```
192.168.1.1.53 > 10.0.2.15.55277: 12816 q: A? google.com. 1/0/1 google.com. A 142.250.193.174
```

The five things I look at in any line:

1. **Who asks whom:** my VM (random source port 55277) to the resolver on port 53. The reply swaps them, and its destination port is my original source port.
2. **Transaction ID (12816):** how a reply is matched to its question.
3. **The question:** the `A` (IPv4) record for `google.com`.
4. **The answer:** `142.250.193.174`.
5. **Whether a reply arrived, and how fast:** about 14 ms between query and reply.

**Noise I learned to ignore:** `bad udp cksum` on outgoing packets. This is a VM artifact (checksum offloading: the virtual NIC fills in the checksum after tcpdump sees the packet). Replies show `udp sum ok`.

## Reading `dig` output

```
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1
google.com.   179   IN   A   142.250.193.174
;; Query time: 52 msec
;; SERVER: 192.168.1.1#53(192.168.1.1) (UDP)
```

- `status: NOERROR`: the lookup succeeded.
- `qr rd ra`: this is a response, I asked for recursion, and the server offers it. The missing flag is `aa` (authoritative), so the answer came from a recursive resolver, not Google's own nameserver.
- `179` is the **TTL**: how many more seconds this answer may be reused.
- `1/0/1` in tcpdump is the same `ANSWER/AUTHORITY/ADDITIONAL` count that dig prints.

## A failure case: retries and failover

In one capture a lookup got no reply. The same question (same transaction ID, **new random source port each time**) was resent every 5 seconds, and after three tries to the first resolver the client moved to the second resolver in `resolv.conf`:

| Time | Sent to |
|---|---|
| 13:23:17 | first resolver (IPv4) |
| 13:23:22 | first resolver, retry |
| 13:23:27 | first resolver, retry |
| 13:23:32 | second resolver (IPv6) |

I reproduced the shape on purpose with a resolver address that doesn't exist:

```
dig +tries=1 +time=2 google.com @10.255.255.1
;; communications error to 10.255.255.1#53: timed out
;; no servers could be reached
```

A client can't tell whether its query or the reply was lost; it just waits and retries. I don't know why the original lookup got no reply, and it worked again a few minutes later.

## TTL experiment

```
$ dig +noall +answer google.com; sleep 5; dig +noall +answer google.com
google.com.   22   IN   A   142.250.207.78
google.com.   17   IN   A   142.250.207.78
```

The TTL dropped by exactly 5 after a 5-second sleep. The resolver is answering from its cache and counting the TTL down; it did not fetch a fresh copy. The first answer already had only 22 seconds left, so the resolver had cached it before my query.

The address (`142.250.207.78`) also differs from earlier lookups of the same name (`142.250.193.174`). A large site can return different addresses at different times.

## What I learned

- Classic DNS here is plain UDP on port 53: no encryption, no connection.
- As I understand it, a reply is accepted when it matches the question, the transaction ID, and the source port my client sent from.
- Resolvers cache answers and count the TTL down.
- Retries reuse the transaction ID but change the source port, and the client fails over to the next resolver in `resolv.conf`.
