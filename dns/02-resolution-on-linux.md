# Stage 2: How a Linux client decides where to look up a name

**Lab:** Kali Linux VM (VirtualBox, NAT networking), NetworkManager, DNS handed out by the network.
**Date:** 2026-11-05

## Goal

Stage 1 showed what a DNS lookup looks like on the wire. This stage is about the client side: when an application asks for a name, who decides where the answer comes from?

## Tools used

| Tool | What it does |
|---|---|
| `getent hosts <name>` | Asks the system's lookup the way an ordinary application does (follows `nsswitch.conf`) |
| `dig <name>` | Asks a DNS resolver directly; never reads `/etc/hosts` |
| `nmcli` | Shows and edits NetworkManager's saved network profiles |
| `grep` | Filters output to the lines I care about |

## 1. Applications ask the system, not DNS

`getent hosts localhost` was answered from `/etc/hosts`. `getent hosts google.com` was not in the file, so the answer came from DNS. `getent` printed an IPv6 address for `google.com`, while `dig +short` printed an IPv4 one. They weren't disagreeing: `getent` asks for the IPv6 (AAAA) record first, while `dig` asks for the IPv4 (A) record by default. A packet capture showed the `AAAA?` query leaving the VM.

## 2. The lookup follows a recipe

```
$ grep '^hosts' /etc/nsswitch.conf
hosts:          files mdns4_minimal [NOTFOUND=return] dns
```

The sources are tried left to right and the first one with an answer wins. `files` is `/etc/hosts`, `dns` is a resolver, and `mdns4_minimal` only applies to `.local` names.

To test the order, I added a fake entry using a reserved documentation address (`192.0.2.1`) for `google.com`:

```
$ echo "192.0.2.1 google.com" | sudo tee -a /etc/hosts
$ getent hosts google.com
192.0.2.1       google.com
```

The local file won even though DNS knows the real address. I removed the entry afterwards.

## 3. Where `resolv.conf` comes from

```
$ cat /etc/resolv.conf
# Generated by NetworkManager
nameserver 192.168.1.1
nameserver <private IPv6 resolver>
```

The file is generated by NetworkManager. `nmcli dev status` shows `eth0` using the connection profile `Wired connection 1`. In that profile:

- `ipv4.dns` is empty (no manual servers)
- `ipv4.ignore-auto-dns` is `no` (accept DNS offered by the network)
- `IP4.DNS[1]` is `192.168.1.1`, the same address as the first `nameserver` line

So the resolver my VM uses is the one the network offered, accepted automatically.

## 4. Overriding it

```
$ nmcli connection modify "Wired connection 1" ipv4.dns "1.1.1.1" ipv4.ignore-auto-dns yes
$ nmcli connection up "Wired connection 1"
$ cat /etc/resolv.conf
# Generated by NetworkManager
nameserver 1.1.1.1
nameserver <private IPv6 resolver>
$ dig google.com | grep SERVER
;; SERVER: 1.1.1.1#53(1.1.1.1) (UDP)
```

The first `nameserver` line changed and `dig` used it; the IPv6 line stayed because I only changed the IPv4 settings. I then reverted the profile (`ipv4.dns ""`, `ipv4.ignore-auto-dns no`) and brought the connection up again.

## What I learned

- Applications use the system lookup, so `dig` doesn't show what an application sees.
- The order in `nsswitch.conf` decides which source answers; a local `/etc/hosts` entry beats DNS.
- `/etc/resolv.conf` is generated output. The real settings live in the NetworkManager profile, and by default they come from what the network offers.
- The first `nameserver` line is the one `dig` used.
